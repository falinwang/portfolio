AI Intake Built for Trust

Integrating AI into a legal intake form for stressed users — designing AI as a bounded supplement that could add context, but never block a request for help.

IMAGE: Hero screenshot — AI Intake Form, final layout
Role

Senior Product Designer

Context

Major legal marketplace · Consumer-facing AI features · Q1 Bundle

Constraint

Feb 1 hard deadline · AI dependency uncertainty · Scope pivot mid-project

What I designed

AI loading states · Error recovery · Two-step flow · Layout architecture

Outcome

Shipped to Q1 deadline

Thesis

"I designed AI as a bounded supplement to a working intake system: it could add missing context, but it could never block a stressed user from submitting a request for help."

The Problem

Users don't know what to say. Attorneys don't know what they're getting.

Anxious users facing legal problems struggle to write effective messages, leaving attorneys without enough context to prioritize or respond.

User problem

Blank form + legal anxiety = low-quality messages. Users don't know what information matters.

Business problem

Poor message quality reduces attorney engagement.

IMAGE: Before state — original intake form
The Constraints

Three pressures hitting at once

The design had to succeed within four hard constraints.

Constraint What it meant for design
Timeline
Feb 1 hard deadline — no extension		 MVP scope was non-negotiable. Any "nice to have" had to be cut or deferred.
Technical
Can't modify competitor messaging template		 Maintaining two parallel templates was cost-prohibitive. Full redesign became blocked mid-project.
Scope
Original plan included full redesign		 Competitor messaging wasn't in scope. Required a strategic pivot on the spot.
AI Dependency
Uncertain if AI would read existing AOP answers		 Risk of AI asking questions the user already answered. Required graceful fallback design.
The Decision That Mattered Most

The pivot: choosing Option 2 over Option 3

When the competitor messaging template issue surfaced mid-project, the team faced a fork.

Option 1 — Parallel templates

Build a new flow, maintain the existing competitor messaging template and the new flow in parallel.

❌ Rejected — engineering cost too high, creates long-term maintenance debt

✅ Option 2 — MVP scope reduction (chosen)

Reduce V1 scope. Add AI questions on top of the existing form only — minimal surface change, maximum feasibility.

Chosen because: existing template is "not the worst on site." A functional AI feature on a working form beats a beautiful but unshippable redesign.

Option 3 — Full redesign including competitor messaging

Redesign everything — contact form, competitor messaging, and new AI layer simultaneously.

❌ Rejected — technically blocked, deadline-impossible

"The question wasn't which option was most elegant — it was which option would actually ship with value intact. Constraint-driven scope cuts are design decisions too."

Chapter 2 — Flow Architecture

The two-step structure: reduce cognitive load first, qualify second

The original form asked for everything at once. The redesigned flow splits the experience into two moments with different purposes.

Step 1 — Message

User answers AOP-specific questions and describes their case (100-character minimum). Focus: get the user writing.

→ Clicks Next → AI begins analysis

Step 2 — AI + Send

AI returns 0–2 follow-up questions → Contact module → "Sign Up to Securely Send" or "Submit My Message".

Q&A is appended as plain text in the existing message body for the dashboard.

Chapter 3 — Micro-Decisions

Micro-Decisions

The details of an AI feature are where trust is won or lost.

1. Text-only loading state

An AI icon in the loading state would signal "this is AI-powered" to the consumer. But the product's AI branding strategy was deliberately attorney-facing. Putting an AI icon here would create a brand inconsistency.

Decision: Text-only loading state — "Analyzing your case details…"

IMAGE: Loading state — before / after

2. Silent failure when AI generates nothing

If the AI fails to generate questions—waiting up to five seconds—showing an error state punishes the user for a system failure they didn't cause. The contact module simply moves up. Unanswered questions do not appear.

Decision: Silent skip to communication preferences. No error message. No broken experience.

3. Non-sticky CTA

An early prototype used a sticky call-to-action. However, incomplete AI questions or reCAPTCHA states could misleadingly imply the request was ready to submit.

Decision: Make the CTA non-sticky.

IMAGE: sticky CTA before/after

4. AI questions moved after Next

Initially, AI questions were placed inside the primary form. We adjusted the flow to trigger AI questions only after the user hits "Next," which proved clearer and more focused for mobile users.

Decision: Separate the AI generation step.

5. Attorney card left, form right, CTA inline

The original layout placed the attorney info panel on the right and the form on the left — with the submit button anchored to the bottom of the attorney card. A user who finished filling out the form had to cross to the right side of the screen to submit.

Decision: Layout flip + CTA inline, consistent with Q&A and review forms.

IMAGE: Layout flip — before (Form Left / Attorney Right) vs. after (Attorney Left / Form Right)
If Not Me

What the default path looked like

Each decision had a lower-effort default. Here's what ships without deliberate choices:

Spinning loader

No text context. Users see an indeterminate spinner and assume the page is broken.

Error state on AI failure

Users see "Something went wrong" for a problem they didn't cause. Damages trust at the worst possible moment.

Disconnected submit button

Users fill out the form and look for a button where the form ends. It's on the other side of the screen.

What I'd Do Differently

The decisions I'd make earlier next time

Include competitor messaging in scope earlier

The scope pivot to Option 2 was the right call given the constraints, but the constraint itself could have been anticipated. A fuller discovery phase would have surfaced the competitor messaging dependency before it became a mid-project blocker.

Map the AOP answer overlap earlier

The risk that AI would re-ask questions already answered in the AOP was discovered mid-design, not at discovery. I'd audit all existing data inputs before designing an AI layer — to understand what the model already knows about the user.

Plan the post-MVP roadmap alongside MVP

The full redesign (Option 3) still needs to happen. By shipping Option 2 first, we've created a temporary state that will require follow-up work. I'd document the post-MVP roadmap explicitly so it's easier to pick up — and harder to deprioritize.
